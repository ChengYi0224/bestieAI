# 05 - 共享 Query 向量檢索與 Prompt 組裝

## 1. 消除重複計算：共享 Query Embedding

在日常聊天模式（`_handle_chat_mode`）下，使用者發送一句話時，系統需要查詢多個維度的記憶：
1. 目標對象的事件記憶（`chat_events`）
2. 使用者自身的生活習慣與偏好（`self_memory`）
3. 若提及朋友暱稱，進行跨對象事件查詢（Cross-RAG）

### 舊有低效做法
每查詢一個庫就向 Gemini API 發送一次獨立的 HTTP 請求計算同句使用者文字的 Embedding，造成 2~3 次重複網路請求，增加 1~2 秒延遲。

### v0.3 共享架構
```
使用者提問："我們上次去沖繩吃什麼？"
       │
       ▼ 打 1 次 Gemini Embedding API (768 維度)
  取得 query_embedding 向量
       │
       ├─────────────────────────┬─────────────────────────┐
       ▼                         ▼                         ▼
查詢 chat_events (contact_id)   查詢 self_memory       查詢 暱稱跨對象庫 (若命中)
(取得 3 則相關事件)              (取得使用者飲食習慣)     (取得相關紀錄)
```
- **效益**：單次對話保證僅有 **1 次** Embedding 網路調用，檢索延遲降低 60% 以上。

## 2. 日常對話 Prompt 組裝結構

為了在維持「秒級回覆（2~3s）」的同時提供極高情商與深厚脈絡，日常對話 Prompt 嚴格控制各區塊的 Token 預算：

```text
[System 角色設定]
你是一位敏銳、有邊界感且真誠的閨蜜 AI...（約 300 字）

[對方人物關係摘要卡]
{300~500 字的 summary_card：包含雙方關係定調、相處模式、雷點與回覆指引}
※ 注意：7 大章節數千字長文保存在 full_history_summary，日常對話絕不載入！

[使用者自我背景]
{檢索出的 1~2 則使用者習慣或偏好}

[歷史事件記憶 (Event RAG)]
{檢索出的 Top-3 則高密度時間事實條目}

[跨對象背景 (選用)]
{若提及他人暱稱時注入的跨對象事件}

[近期對話上下文]
{最近 20~30 則原始私訊紀錄}

[對話歷史]
{最近 3 輪與 AI 閨蜜的討論紀錄}

[使用者現在說]
{使用者最新傳來的訊息}
```

---

## 3. 效益總結

1. **資訊高密度**：事件條目均為濃縮事實，3 則條目通常只佔 150 Token，卻完整交代了時間、地點與核心經過。
2. **無雜訊干擾**：徹底去除口語碎詞，AI 聚焦於事件本身。
3. **極致低延遲**：共享向量 + 輕量卡控制 Prompt 在 2,500 Token 內，Gemini Flash 回覆穩定在 2~3 秒內完成。
