# 01 - 微觀事件提煉與時間滑動窗口（Temporal Sliding Window）

## 1. 核心定位與 RPD / Embedding 瓶頸突破

傳統 RAG 以 40 則訊息固定切塊面臨兩大硬傷：
1. **RPD（每日請求次數）先於 Token 耗盡**：5,000 則訊息若切 40 則會觸發 125 次 LLM 呼叫，極易榨乾免費層每日 Request 額度。
2. **Embedding 呼叫頻率過高**：產出 400+ 條碎事件，易撞上 Embedding 100 筆/分上限。

### 最佳解：400 則時間感知滑動窗口 + 12 則 Overlap
- **單批目標容量（Target Batch）**：**400 則訊息**（硬上限 500 則）。僅佔 Gemini Flash-lite 百萬 Context 的 0.5%，語意理解更連貫。
- **時間感知自然切分**：若對話靜默超過 6.0 小時且已累積達 200 則以上，視為話題自然結束點提前切分。
- **邊界重疊緩衝（Overlap = 12 則）**：相鄰兩批交界處保留 12 則重疊訊息，確保起承轉合不被機械式切斷。
- **解除條數限制（事實密度提煉）**：徹底移除舊版「1~4 條」桎梏，改為有多少客觀事實就提煉多少條；若整批皆為閒聊則輸出「無重要事件」。
- **即時增量落盤**：每提煉完 1 批，立即寫入本地 SQLite 快取（`status='raw'`），徹底杜絕中斷遺失。

---

## 2. 成果效益對比（以 5,000 則對話為例）

| 指標 | 舊版切塊機制 (40 則固定) | 新版時間滑動窗口 (400 則 + 12 重疊) | 效益提升 |
| :--- | :--- | :--- | :--- |
| **提煉 API 呼叫次數** | 125 次 Request | **12 ~ 14 次 Request** | **節省 90% RPD 消耗** |
| **產出事件總數** | 460+ 條（語意稀疏碎片） | **50 ~ 80 條（高密度精華）** | 記憶條目質量大幅提升 |
| **Embedding 向量計算** | 需打 5 批次，易撞 429 | **1 批次即可算完 (<= 100 筆)** | 0 觸發 429 速率超限 |
| **邊界話題斷裂** | 無重疊，容易腰斬關鍵字 | 保留 12 則上下文重疊 | 話題語境完整無損 |

---

## 3. 15 RPM 速率節流（Pacing Delay）

- **系統設定**：`GEMINI_PACING_DELAY: float = 4.2` 秒。
- **批次發送間隔**：每完成一個批次的提煉，強制休眠 4.2 秒，請求頻率維持在約 14.2 RPM，平穩安全。
