# 03 - 同質無損融合與多群批次打包（Batch Cluster Consolidation）

## 1. 核心任務與 RPD 節流革新

當「時序向量分群（Complete Linkage 0.90）」篩選出若干個包含 $\ge 2$ 條事件的候選群組時，系統進行語意無損融合。

### 傳統痛點：1 群 1 Request 迅速榨乾 RPD
若分群產出 20~40 個候選 Cluster，逐一呼叫 LLM 會消耗 20~40 次 Request。對於每日 500~1,500 RPD 的免費層配額而言，Request 數量遠比 Token 更先見底。

### 最佳解：多 Cluster 批次打包融合（一次 20 群）
- **打包上限**：`CLUSTERS_CONSOLIDATION_BATCH_SIZE: int = 20`。
- **單次 Context 負擔**：20 個小群組（每群 2~4 條，總計約 50 條文字）僅約 1,500 Tokens，完全在 Flash-lite 處理能力之內。
- **結構化傳輸**：透過 XML `<cluster id="...">` 標籤分組傳遞，要求模型嚴格在各群組內部進行融合，各群組之間彼此隔離，互不混雜。
- **成效**：融合階段的 API Request 呼叫次數直接**縮減 90% 以上**（由 20~40 次壓縮為 1~2 次！）。

---

## 2. 核心原則：「只去重、不有損」

1. **同主題細節補全（同質融合）**：
   - 目的：將破碎在不同 Batch 的同一事件融合成一條高密度條目。
   - 要求：所有具體實體（人名、地名、餐廳、物品、承諾、決策）**100% 完整保留**，不得丟失細節。
   - 禁令：**嚴格禁止模糊概括**（如寫成「兩人聊了旅遊與生活」等空泛廢話）。
2. **不同主題各自獨立（異質保留）**：
   - 若向量模型因偶然的高詞頻重疊將兩件本質不同的事聚在同一個 Cluster，LLM 必須辨識出語意差異，**分別作為獨立條目回傳**，嚴禁強行湊成一筆。

---

## 3. 仲裁案例比對

### 案例 A：同質話題無損融合（3 條合為 1 條）

輸入 Cluster：
```text
- [2026-08-15] 兩人討論想去沖繩玩。
- [2026-08-15] 兩人規劃去沖繩想吃石垣牛與海葡萄。
- [2026-08-15] 討論沖繩當地租車自駕的預算與保險。
```

輸出（融合條目）：
```text
[2026-08-15] 兩人討論規劃沖繩自由行，提及想品嚐石垣牛與海葡萄，並進一步研究當地租車自駕的預算與保險事宜。
```
> **檢視**：沖繩、石垣牛、海葡萄、租車自駕、預算保險全部保留，無任何資訊損失，但在向量庫中只佔據 1 條精確索引！

### 案例 B：異質話題獨立保留（2 條維持 2 條）

輸入 Cluster（同日均提及車輛交通）：
```text
- [2026-08-15] 討論沖繩自由行租車自駕的費用。
- [2026-08-15] 對方提到自己上班路上機車拋錨，心情很糟。
```

輸出（保持分離）：
```text
- [2026-08-15] 討論沖繩自由行租車自駕的費用預算。
- [2026-08-15] 對方上班途中機車拋錨導致心情煩躁，向我抱怨。
```
> **檢視**：LLM 成功識別「旅遊規劃」與「突發倒楣事」為不同事件，保持各自獨立。

---

## 4. 提示詞規格與降級容錯
- 提示詞範本：`app/prompts/events/consolidate_batch.txt`。
- 容錯機制：若批次解析中某個 Cluster 格式不符合預期，系統自動降級回退，保留該群組原始事件條目，確保資料 100% 不丟失。
